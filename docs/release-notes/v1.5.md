# pg_hardstorage v1.5

> Distilled for operators; the full commit-level detail is in the
> [`CHANGELOG`](../changelog.md).

This is a **minor** release: several error codes change and two commands
change default behaviour — see [Upgrade notes](#upgrade-notes). Nothing on
disk or on the wire changes; the 24-month schema promise is untouched.

## Continuous archiving had no unit to run it

The packages shipped `pg_hardstorage.service` and `pg_hardstorage@.service`,
and the getting-started tutorial, a runbook and all three migration guides
pointed at them to "supervise the WAL streamer". Both run
`pg_hardstorage agent`, which executes scheduled backups and retention and
**never opens a WAL stream**. An operator who followed the tutorial got
periodic base backups and no continuous archiving, with nothing to indicate
the always-on part of the product was absent.

`pg_hardstorage-wal-stream@<deployment>.service` now ships in every package
(deb, rpm, Arch, nfpm), templated on the deployment, and the documentation
uses it. (#56, reported by @marsqd.)

## Retention follows the policy you declared

Two bugs, one from each direction (#66, reported by @marsqd).

The documentation said `rotate` runs after every backup commit. It never
has: retention is applied by the agent's scheduled `rotate` task or by
running `rotate` yourself. A deployment that scheduled `backup` but not
`rotate` kept every backup it ever took — the reporter had 78 fulls under a
`keep_for: 7d` policy. The docs now say so plainly and show what to
schedule.

The follow-up was worse. A manual `rotate <deployment>` ignored the
deployment's `retention:` block and planned with the built-in GFS defaults,
while the scheduled task used the block. One deployment, two retention
policies, depending on who ran it — and the cron form the docs recommend
would have applied the wrong one. A deployment configured to keep *more*
than GFS would have had backups soft-deleted that its own policy protects.

`rotate` now resolves policy per deployment: explicit `--policy`/`--keep-*`
flags, otherwise the deployment's block (through the same code the agent
uses), otherwise the defaults — and every plan line says which, e.g.
`count {KeepFulls:2} (from pg_hardstorage.yaml)`. A retention block that
does not parse, or a `pg_hardstorage.yaml` that will not load, refuses
instead of falling back.

## Errors that name the right thing

Automation routes on error codes, so a code that names the wrong system
sends the page to the wrong person.

- **A split-brain never carried its documented code.** Two clusters
  archiving into one lineage were reported as `wal.push_failed` or
  `wal.stream_permanent`; `splitbrain.*`, which the reference tells you to
  route on, appeared only in the message text. It is now the code.
- **A PostgreSQL connection failure was `storage.unreachable`.** "The
  database is in crash recovery" reached whoever owns the storage bucket.
  It is now `pg.unreachable`; Patroni's REST endpoint being down is
  `patroni.unreachable`. Both keep exit code 8.
- **"Requested WAL segment has already been removed" was `internal`** — the
  "we don't know what this is" bucket — for the most predictable failure a
  backup of a busy database has. It is now `backup.wal_recycled`, which says
  it is a sizing condition, not damage, that retry is safe, and to raise
  `wal_keep_size`. (A running `wal stream` does *not* prevent it: its slot
  holds WAL the streamer has not consumed, while a long backup needs WAL from
  its own start point.) And the underlying cause is fixed: `--include-wal`
  backups now pin their WAL with a temporary replication slot, as
  `pg_basebackup` does, so a busy database no longer recycles it
  mid-backup.
- **A restore said `postverify_failed` when the host was simply missing an
  extension.** Backups of Patroni/Spilo clusters preload `bg_mon`; restored
  onto stock PostgreSQL, the boot check died before reading a data page.
  "Your backup did not survive" is the most expensive wrong answer this tool
  can give mid-DR. A missing preloaded library is now treated like a missing
  `pg_ctl` — the check is skipped with the library named — unless
  `--verify-restore required` demands proof.

## A backup that cannot be restored no longer looks like one that can

A base backup taken without `--include-wal` is only restorable once the
WAL written during it has been archived. With no archiving running, the
product reported a successful backup, and a restore of it produced a data
directory whose recovery waited forever. Our own first-backup tutorial did
exactly this. Now `backup` warns when a backup is **not restorable yet**,
and `restore` refuses it immediately (`preflight.backup_wal_missing`,
exit 4) instead of hanging. Both conditions are narrow: they fire only
when the backup carries no WAL *and* the repository has none on its
timeline, so a deployment with working archiving never sees them.

The same gap affected DR replicas. `repo replicate` copies WAL only with
`--include-wal`, and a default replica of a WAL-archiving source reported
"replication clean" while being unable to restore those backups. It now
says so.

## `partial dump` works on real clusters

`partial dump` restores into a throwaway sandbox and reads it with
`pg_dump`. It connected as the host's login name, so it only worked where
that happened to be a role in the backed-up cluster, and it honoured the
restored cluster's own `pg_hba.conf`, so any cluster requiring scram, md5,
LDAP or certificates was out of reach. The sandbox now
uses its own trust-only rules on a socket nobody else can reach, connects as
`postgres`, and takes `--pg-user` for clusters initialised under another
name.

A table that does not exist was reported as a `pg_dump` failure (exit 1);
the guard meant to catch it could never run on a current PostgreSQL. It is
now `partial.dump_no_tables`, exit 6, with the advice to pass `--database`.

## The LLM helper

The helper checks every command it suggests against the real CLI and asks
the model to fix anything wrong. That check rejected valid commands — flag
spellings the CLI accepts, and `--repo`/`--pg-connection` that the CLI fills
in from a configured deployment — and then talked the model into genuinely
invalid ones (`--conn`, `--pg-conn`). It now accepts exactly what the binary
accepts. The system prompt shrank from 150 KB to 64 KB, slow local models
are no longer cut off at five minutes, and a stream that goes silent is
detected and interrupted.

## A full review of the code

Before this release every line of Go in the project — about 184,000 —
was read for defects that can actually happen, not for style. That
review found about 205, eleven of them critical. All are fixed, each
with a regression test that fails without the fix; the
[`CHANGELOG`](../changelog.md) lists them. The ones an operator is most
likely to have met:

- **Restores through the compatibility shims lost WAL.** A
  `pgbackrest restore`, `barman recover`, `wal-g backup-fetch` or
  `barman-cloud-restore` stopped at the backup's consistency point
  instead of replaying the archive, and the `wal-g wal-fetch` /
  `pgbackrest archive-get` shims told PostgreSQL "no such segment" on
  *any* error — an S3 outage ended recovery early and promoted.
- **`kms rotate` stranded WAL.** It rewrapped backup manifests but not
  WAL segment manifests, so WAL archived before a rotation could not be
  decrypted afterwards.
- **GCS could lose chunks.** An upload error whose text happened to
  contain "412" was taken for "already exists".
- **Incremental restores of clusters with tablespaces** put the
  tablespace data in the wrong place and reported success.
- **Recovery settings leaked across restores** through
  `postgresql.auto.conf`.
- **`repo gc` could race a writer**, and on a large shared repository
  took many minutes. It now fences every writer — backups, WAL
  streaming, logical streams, replication, bundle import — and is
  several times faster.
- **The soak harness could report PASS** for a cell that stayed dead,
  for faults that did nothing, and for a mistyped fault catalogue.
  Soaks run for this release use the corrected harness.

## How this release was tested

The final campaign ran on the release commit:

| Gate | Result |
|---|---|
| unit tests under `-race`, all 170 packages; again in shuffled order (8 seeds) | pass |
| fuzzing (every target, 60 s each), mutation checks | pass |
| scenario corpus | 169 pass, 3 skipped (need Kubernetes) |
| integration, Patroni, WAL-stream, stress, compat smoke, release gate, doc examples | pass |
| 8-hour soak, 21 cells (Debian, Ubuntu, Rocky, Fedora × PostgreSQL 15–18) | **PASS**: 4,816 backups and 961 restore verifications, none failed, under 4,813 injected faults |
| 5.5-hour soak, `enterprise_heavy`, 4 cells | 100 backups and 20 restore verifications, none failed, under 100 injected faults and 27 retention windows. Stopped by the host's disk guard, not by a failure |

`enterprise_heavy` seeds 10 GB per cell and runs a 16-client write load
while backups, restores and faults proceed. That
profile had never been able to start (its seed step used `sudo` from a user
without sudo rights). Getting it to run found most of the
error-classification bugs above, and several defects in the test harness
itself — including that its write load died at the first fault that
restarted PostgreSQL and was never restarted, so an earlier "passing" heavy
soak had not in fact kept the load up. The writer is now supervised and its
uptime reported.

## Upgrade notes

1. **`pg.unreachable` / `patroni.unreachable` replace `storage.unreachable`**
   for PostgreSQL and Patroni connection failures. Exit code 8 is unchanged.
   Automation matching the string `storage.unreachable` to detect a down
   database must match `pg.unreachable`.
2. **`backup.wal_recycled`** replaces `internal` for recycled-WAL backup
   failures. Exit code 1 is unchanged.
3. **Split-brain refusals now carry `splitbrain.*`** — previously
   `wal.push_failed` (wal push) or `wal.stream_permanent` (wal stream).
   Exit code 1 is unchanged. Rules written against the documented code
   start matching; rules written against the old codes must add it.
4. **`rotate <deployment>` now follows the deployment's `retention:` block**
   when no retention flags are given. If you relied on the GFS defaults
   while a different block was configured, dry-run first and check the
   `policy:` line. A `pg_hardstorage.yaml` that fails to load now stops
   `rotate` (without explicit flags) rather than being ignored.
5. **`partial dump`** connects to its sandbox as `postgres` (`--pg-user` to
   change), and a table that is not found exits **6**, not 1.
6. **`restore --verify-restore auto`** (the default) skips the boot check, with a warning,
   when the host lacks a library the source cluster preloaded. Use
   `required` if a skipped check must fail the restore.
7. **`restore` refuses a backup whose WAL exists nowhere** —
   `preflight.backup_wal_missing`, exit 4 — where it previously produced a
   data directory that never finished recovery. `--skip-gap-check`
   overrides. `backup` results gain `self_contained`, `wal_archived` and
   `restore_needs`.
8. **New unit** `pg_hardstorage-wal-stream@.service`. Enable it per
   deployment for continuous archiving:
   `systemctl enable --now pg_hardstorage-wal-stream@db1`.
9. **Approvals need a trusted approver roster.** Set
   `PG_HARDSTORAGE_APPROVAL_ROSTER` (default `<config>/approvers`); at
   least `PG_HARDSTORAGE_APPROVAL_MIN_THRESHOLD` (default 2) approvals
   from roster keys are required, every request needs an exact
   `--target`, and an approval is used up by the operation it gates.
   **With no roster, every approval is refused.**
10. **`-o json` prints one document.** Events that used to precede the
    result on stdout now go to stderr as NDJSON. Use `-o ndjson` to keep
    everything on stdout.
11. **Restore hosts need the keyring.** `restore`, `repair`, `jit` and
    `audit export-bundle` no longer create a signing keypair when the
    keyring is empty; they fail with `notfound.signing_key` (exit 6).
    Run `keyring install` on a DR host before restoring.
12. **wal-g shim deployment names.** A dotted `PGHOST` now maps to a
    sanitised name (e.g. `db_example_com`), starting a new lineage;
    take a fresh full backup after upgrading. A Unix-socket `PGHOST`
    maps to `default`.
13. **Exit and error codes.** `repo gc` blocked by a live backup lease:
    `conflict.gc_backup_in_flight`, exit 7 (was exit 1). `repo check`
    read errors: `repo.check.manifests_unreadable`, exit 1 (was 9). A
    KMS that refuses the credentials: `auth.kms_access_denied`, exit 3.
14. **Stricter refusals.** A missing `-c` file is an error;
    `partial restore` exits non-zero for a table it could not find and
    refuses incremental backups; `hold add` will not weaken an active
    hold without `--force`; `repo wipe` refuses while legal holds exist;
    the barman/pgbackrest shims refuse target times without a UTC offset.
15. **LLM skills** are no longer loaded from `./share/skills` in the
    working directory; set `PG_HARDSTORAGE_SKILL_DIR`.
16. **`audit verify-bundle`** requires a trusted signer (the local
    keyring key, `--trusted-key` or `--trusted-fingerprint`).

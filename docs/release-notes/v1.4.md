# pg_hardstorage v1.4

> Released 2026-09-08. Distilled for operators; the full commit-level
> detail is in the [`CHANGELOG`](../changelog.md).

This is a **minor** release because a number of exit codes and status
values change — see [Upgrade notes](#upgrade-notes). Nothing on disk or
on the wire changes; the 24-month schema promise is untouched.

Its centre of gravity is the **compatibility layer**: the pgBackRest,
Barman and WAL-G shims, and the `compat translate` config translators.
That surface had unit tests and a passing scenario suite, and it was
still broken in ways those could not see — because the tests stubbed
the dispatcher, and the translators were never asked to produce
something the loader would actually load.

Driving the shims against the *real* tools — pgBackRest 2.59.1, Barman
3.20.0, WAL-G — and a live PostgreSQL is what found the following. The
same pass covered a 32-cell / 2 h chaos soak, which turned out not to
be measuring the thing it exists to measure.

## The three that lose data, or make it unreachable

**Every restore driven through a compat shim produced an unbootable
cluster.** The shims dispatch the native CLI *in-process*, so
`os.Executable()` inside `WriteAutoRecovery` returned the **shim's**
path — and that literal path went into the restored cluster's
`postgresql.auto.conf` as the `restore_command`. At recovery time
PostgreSQL ran `<shim> wal fetch …`; the multicall binary dispatches on
`argv[0]`, did not recognise itself under that name, and exited 2.
That is neither 0 (delivered) nor 6 (absent), so the embedded tail did
what it is designed to do and aborted — and the cluster died with
*"child process was terminated by signal 6"*.

The restore itself reported success. The failure surfaced only at first
boot, to whoever tried to start the cluster. DR through the shims —
their entire purpose — did not work.

**A CNPG replica could promote with unreplayed WAL still in the
repository.** `barman-cloud-wal-restore` collapsed every native failure
to exit 1. PostgreSQL reads *every* plain non-zero exit from a
`restore_command` as end-of-archive, so an S3 outage, an expired
credential, a keyring refused for its file mode, or a chunk swept by
`gc` all read as "there is no more WAL" — and the replica promoted
behind the data it had been asked for. This is precisely the mode the
product's own embedded `restore_command` tail was written to prevent,
reintroduced in the one path where the shim *is* the
`restore_command`.

**All three config translators emitted YAML the loader rejects**, so
the documented migration path — translate, drop in, use — could not
work at all. `internal/config` decodes with `KnownFields(true)`, and
the pgBackRest translator emitted `keep_full_count` plus an
`encryption:` block, the Barman translator emitted `slot:`,
`parallelism:`, `compression:` and `backup:`, and the WAL-G translator
emitted `encryption.{kek_ref,passphrase_env}` — none of which exist in
`DeploymentConfig`. Every migration hit a config that would not load,
after the operator had already dropped it into
`/etc/pg_hardstorage/`.

A round-trip test now pushes all three translators' output through the
production loader, so this class of drift is a build failure instead of
something an operator finds mid-cutover.

## The shims, as an operator actually invokes them

`pgbackrest --stanza=db1 backup` — the canonical cron line, with
everything else in `pgbackrest.conf` — **failed**, contradicting the
migration guide's promise that an existing cron runs unchanged. The
stanza now falls back to the matching `pg_hardstorage.yaml` deployment,
with explicit flags still winning.

`--retention-full` was parsed and then **silently dropped**: no native
argument, no warning. An operator's `backup --retention-full=7`
appeared to run unchanged while retention reverted to the native
default. Silent policy drift is the worst failure mode a backup tool
has. Retention is applied by `rotate`, not `backup`, so the shim
cannot forward it — but it now says so, and names both ways to set it.

`barman check --nagios` was broken in **both** directions at once. The
template read `.ok` and `.summary`, which the `doctor` result does not
have, so it rendered `BARMAN CRITICAL - <no value>` for a *healthy*
server; and `doctor` was invoked without `--exit-on-issues`, so the
process exited 0 in every state. A healthy server paged, and a server
whose PostgreSQL was down monitored green.

That second half had a deeper cause. **`doctor <deployment>` ignored
the deployment** — the positional has always been advertised, and every
probe walked the whole fleet, so the answer to "is db1 healthy?" was a
fleet verdict. And **`doctor` never connected to PostgreSQL** at all:
it inspected paths, repositories, keys and manifests, and a deployment
whose server was unreachable reported healthy because nothing in the
report had ever opened a connection.

Also fixed: `barman-wal-archive` rejected the classic two-argument
`archive_command` (`barman-wal-archive db1 %p`) — the single most
common drop-in point there is, and PostgreSQL retries a failing
`archive_command` forever, so WAL piled up. `list-backup --minimal`
printed one blank line per backup because its template named a field
that does not exist, which to the `| head -1` scripts the flag exists
for is indistinguishable from "no backups". `wal-g backup-push` failed
out of the box on PG 15/16 and on unconfigured PG 17, because it mapped
wal-g's tool-level delta default onto PostgreSQL's incremental
protocol; it now probes the server and takes a full backup, with a
warning, when the prerequisites are missing.

A long tail of pgBackRest and Barman flags that died as bare
`unknown flag` — against a documented promise that anything unsupported
refuses *with a pointer at the native equivalent* — now parse, map, or
refuse by name. Among them `--repo1-type=file`, which is pgBackRest's
own spelling for a local repository and the most common one there is.

## Corruption no longer reads as a tool bug

A torn page caught by PostgreSQL 18's base-backup checksum verification
surfaced as `code: "internal"` — the bucket reserved for *we do not
know what this is*. So the most urgent signal the tool can emit, **your
production data is damaged**, was indistinguishable from a bug in the
tool, and automation keyed on error codes routed it to whoever triages
tool bugs.

`XX001` / `XX002` now map to `source_corruption.*` with operator
guidance that says plainly: this is the source database, do not retry
the backup, keep and verify what is already in the repository.
Restoring a backup id that does not exist likewise reports
`notfound.backup` rather than `internal`.

## The soak was not measuring what it claimed

The WAL-stream sidecar is a `docker exec`, so it dies with the
container — and the soak's `signal` fault primitive kills containers on
purpose. Nothing restarted it. **The first signal fault in a cell ended
continuous WAL archiving for the rest of that cell's run**, and 30 of
32 cells took at least one.

The tell was in the report the whole time. Cells whose first signal
fired early carried 1.3–2.3 GB of `wal_repo_lag_bytes` against 33–67 MB
for cells that took none, and 7 of 32 deployments had no WAL in the
repository at all. That was read as *the streamer fell behind*. The
streamer was not there. The sidecar is now supervised, and the report
distinguishes "was interrupted" from "fell behind".

Two more of the same shape. A cell could be **dead for 44 minutes and
still PASS**: the `signal` fault ran `docker start` and never checked
it worked, and nothing else watches a cell that is down with no fault
in flight. And `checkpoint_storm` could apply as a **complete no-op** —
wrong OS user, no `psql` in the image, PG down — while the report
recorded it as applied, voiding any correlation drawn from it in either
direction.

Finally, PG 18 × `torn_page` failed the fault catalogue's own pass
criterion *by construction*. PostgreSQL 18 verifies page checksums
during `BASE_BACKUP`, so an injected torn page is refused at backup
time rather than surfacing later at restore — an **earlier** detection,
which the criterion counted as `backup_failed`. Every such cell aborted
on the first hit and burned the rest of its window; all five cell
failures in the 2 h soak were this.

## Upgrade notes

Nothing on disk or on the wire changes — the 24-month schema promise is
untouched — but several exit codes and status values do, and automation
may notice:

1. **`doctor` now connects to PostgreSQL.** `doctor --exit-on-issues`
   can exit **10** where it previously exited 0, because a deployment
   whose server is unreachable now reports `pg.unreachable` instead of
   reporting healthy. **A `doctor` that appeared to pass before may now
   fail — that is the bug surfacing, not a regression.** It also opens
   one short-lived, bounded connection per configured deployment, which
   is new outbound activity for that command.
2. **`doctor <deployment>` now scopes to that deployment.** It
   previously reported on the whole fleet regardless of the argument.
   A name that matches nothing still produces the report — the
   environment checks are what an unconfigured host needs — but adds a
   `doctor.unknown_deployment` warning naming the deployments that do
   exist.
3. **`restore` with a backup id that does not exist exits 6**
   (`notfound.backup`), not 1.
4. **`barman check --nagios` returns real Nagios exit codes** —
   0 OK, 1 WARNING, 2 CRITICAL, 3 UNKNOWN. It previously exited 0 in
   every state, so any monitoring built on it was inert; expect it to
   start reporting.
5. **`barman-cloud-wal-restore` exits 126** for any failure that is not
   "segment absent" (which stays 1). This is the silent-promotion fix:
   126 is above PostgreSQL's `wait_result_is_any_signal` threshold, so
   recovery aborts instead of promoting. **Do not "fix" a wrapper by
   collapsing it back to 1.**
6. **`lint` can now report `"status": "incomplete"`** for a config that
   parses but contains a deployment with no `pg_connection` or no
   `repo`. Automation testing `status == "valid"` will see it.
7. **`compat translate --output <path>` is now `--out-file <path>`.**
   The old spelling never worked — it collided with the root's
   persistent `-o/--output`, which selects an output *format*, so the
   documented command died with `unknown output format`. Nothing that
   previously worked breaks.
8. **Source-corruption failures report `source_corruption.*`**, not
   `internal`. The exit code is unchanged (1).

Package upgrades, repositories, manifests and WAL are unaffected. No
migration.

# pg_hardstorage v1.2

> Released across 2026-08-08 (`1.2.0`), 2026-08-09 (`1.2.1`), and
> 2026-08-17 (`1.2.2`). Distilled for operators; the full
> commit-level detail is in the [`CHANGELOG`](../changelog.md).

This is a **minor** release because it adds surface — `restore
--to-latest`, the `backup --tde` family, an append-only repository
mode, and the `keyring install` command are all new — but its centre
of gravity is **correctness under failover**. The 1.2 line is where
the Patroni story stopped being "streams WAL across a promotion" and
became "**does not silently lose or corrupt data across a promotion,
and can prove it**."

Almost everything here was found the same way: an adversarial **chaos
gate** that stands up a real three-node Patroni cluster and drives real
faults — switchovers, hard leader kills, DCS (etcd) outages straddling
the TTL, compound storms, and retention janitors running mid-storm —
then **restores and boots** the backups taken during the chaos. Each
silent-data-loss class below is a bug that gate surfaced and that now
has a permanent regression net.

Everything is **backward compatible**. No on-disk migration, no config
migration, and nothing changes encryption posture on upgrade. The new
knobs are opt-in and defaults preserve existing behaviour.

---

## The theme: no data lost across a Patroni failover

A promotion is the moment a WAL archiver is most likely to lose bytes
silently — the replication slot moves, a timeline forks, and "nothing
archived on the new timeline yet" looks exactly like "fresh
deployment." 1.2 closes that gap end-to-end.

### Failover gaps are detected, recorded, and refused — not skipped

When a slot is recreated on the new leader with a `restart_lsn` ahead
of the last position the agent confirmed, the intervening WAL is a
genuine hole. The leader-follow coordinator now computes that gap
(including on a *found* slot that Patroni recreated at promotion, which
previously masked the hole), records it durably, and **restore refuses
a PITR target that lands inside it** rather than promoting silently
behind the data you asked for. The archive-frontier lookups fall back
to the nearest prior timeline, so a freshly-promoted timeline with
nothing archived yet is never misread as an empty deployment.

### A recreated slot no longer kills the streamer (`1.2.1`)

The resume floor treated any start below the slot's `restart_lsn` as
proof the WAL was recycled. But `restart_lsn` is a retention *floor*,
and Patroni recreates permanent slots at the promotion point, so after
a failover the recreated slot routinely sits above a perfectly servable
archive frontier. `wal stream` now warns and **attempts** the resume —
PostgreSQL is the arbiter — and only walsender's own "requested WAL
segment has already been removed" is treated as the terminal loss, with
the same code and re-anchor remediation as before. Real losses read
exactly as they did; the false positives that stopped streaming in a
self-healing situation are gone. Found by the new DCS-outage fault on a
demotion storm.

### Foreign WAL is refused at the first byte

Every `restore_command` now arms a cluster-identity check, and `wal
stream` / `wal push` refuse WAL whose `system_identifier` doesn't match
the deployment's lineage — a `pg_upgrade`, a cloned datadir, or a
misconfigured fleet streaming a different cluster's WAL into an existing
timeline is refused by name at the first segment, instead of
interleaving two clusters and corrupting point-in-time recovery.

### `wal audit` sees holes that straddle a timeline change

Gap detection used to be structurally blind exactly at the failover
boundary. `wal audit` and the chaos gate now detect WAL holes across a
timeline transition, and a standby built over a holed archive — which
would otherwise stay *up and healthy while frozen at the hole* — is now
warned about up front.

## Storage janitors no longer lose data on unusual-but-valid names (`1.2.2`)

A deployment or backup ID may legitimately contain dots — only path
separators and control characters are barred. Several storage walks
matched the commit-staging-temp marker (`.tmp.` / `.json.tmp.`) against
the **full** object key instead of just the filename, so a committed
object under a name like a backup `db1.full.tmp.abc` or a deployment
`db.json.tmp.x` could be mistaken for an in-flight temp and skipped or
swept. The consequences were all silent data loss:

- `repo gc` could delete a live backup's manifest, or reap a
  still-referenced chunk;
- `wal prune` could advance its frontier past a live backup and delete
  the WAL it still needs;
- `repo replicate` could omit a backup from a DR replica;
- the archive-frontier lookups could report "nothing archived,"
  blinding failover-gap detection;
- the foreign-cluster `system_identifier` guard could fail open.

Every affected matcher is now scoped to the key's **basename**, so a
committed object is never mistaken for a temp regardless of its
deployment or backup name. These paths were reachable only for the
unusual dot-`tmp` naming; no conventional deployment was affected, but
if yours happened to use such a name, upgrade.

## Restore correctness

- **Non-contiguous chunk lists are refused, not scrambled (`1.2.2`).**
  The file-reassembly path wrote chunks in slice order and checked only
  per-chunk length and total size, so a reordered-but-same-size chunk
  list would restore byte-scrambled data that passed every check. It
  was safe in practice (an upstream validator enforces contiguity), but
  the byte-order of restored data no longer rests on a single guard:
  reassembly now confirms each chunk lands at its recorded offset.
- **`restore --to-latest` (`1.2.0`).** End-of-archive recovery had no
  CLI spelling — a plain restore writes no recovery files. `--to-latest`
  arms recovery to replay every archived segment forward from the base
  backup.
- **The documented cascade unwind works verbatim (`1.2.0`).** `backup
  delete --cascade` followed by `backup undelete` now round-trips as the
  docs describe, ordering ancestors first so a chain resurrects cleanly.
- **`backup undelete` re-checks the WAL, not just the chunks (`1.2.0`).**
  Resurrecting a tombstoned backup whose archived WAL was pruned in the
  meantime now records the resulting gap, so a later unbounded restore
  refuses precisely instead of promoting behind.
- **`--to <time>` rejects malformed 12-hour clocks (`1.2.2`).** `13am`,
  `0am`, and `0pm` used to resolve to plausible-but-wrong instants (a
  `recovery_target_time` twelve hours off); they are now rejected loudly.

## TDE-source awareness is complete on `backup` (#48, `1.2.2`)

pg_hardstorage backs up a Transparent-Data-Encryption cluster (CYBERTEC
PGEE, pg_tde, EDB TDE) transparently — `BASE_BACKUP` and replication
deliver plaintext over the wire, so no flag is required for the backup
to succeed. What was missing is **posture metadata**: `backup` accepted
neither a `--tde` flag nor the deployment's `tde:` block, so the
`source_tde` manifest stamp the docs promised was always absent.

`backup` now takes `--tde`, `--tde-engine`, and `--tde-key-ref`, and
also reads `tde.enabled` from the deployment config (flags win when
both are set). The declaration is stamped onto the manifest as
`source_tde` and shown in the backup result. That stamp is what lets a
later restore refuse a **vanilla-PostgreSQL** target loudly — instead of
writing a data directory full of ciphertext — and lets `wal push` skip
the on-disk header parse that is meaningless against encrypted segments.
The field is additive and omitted when TDE is not declared, so nothing
changes for non-TDE deployments. See
[TDE awareness](../explanation/tde-awareness.md) for the full story,
including *why* a plain backup/restore of a TDE cluster already works.

## Kubernetes: the keyring the chart documented now loads

- **The sidecar chart's keyring actually starts (#46, `1.2.0`/`1.2.1`).**
  Kubernetes rewrites Secret file modes under `fsGroup`, and the
  keystore's owner-only permission gates (which demanded exactly `0600`)
  refused the `0400` a mounted Secret produces — so the keyring feature
  could never start. The gates now refuse what they always meant to (any
  group or other bit), and a new `install-keyring` initContainer runs
  the new **`pg_hardstorage keyring install`** command — built for
  distroless images — to copy the material into an in-memory volume with
  owner-only modes. A misconfigured Secret now fails the init step
  loudly instead of producing a keyless pod.
- **The initContainer runs with the hardened security context (#49,
  `1.2.2`).** The `install-keyring` step referenced an undefined
  `containerSecurityContext` value and so rendered with an empty
  `securityContext`; it now uses the same hardened
  `.Values.securityContext` as the main container
  (`allowPrivilegeEscalation: false`,
  `readOnlyRootFilesystem: true`, `capabilities: drop: [ALL]`). Sidecar
  chart `0.1.2`.

## Storage backends: fewer silent hangs and lies

- **A dead SFTP connection is an error, not a forever-hang (`1.2.0`).**
  `ssh.ClientConfig.Timeout` covers only the dial; a mid-operation
  network drop parked a worker indefinitely. An SSH keepalive prober now
  tears down a dead transport and the next operation reconnects, so a
  stalled backup fails cleanly and recovers when the network returns.
- **`scp` stops reporting success as failure and vice versa (`1.2.0`).**
  A successful read that failed on `Close` was reported as an error, and
  a failed remote read looked like an empty object; both are fixed, and
  the `scp://` and `sftp://` backends now run the full storage-contract
  suite in a container.

## Append-only repositories (`1.2.0`)

A repository can now be operated **append-only**: manifests, integrity
runs, and DSA records are written but never rewritten in place, so a
compromised agent cannot silently alter history. This composes with the
existing WORM/Object-Lock retention rather than replacing it.

## The chaos gate, and how these bugs were found

Most of 1.2's fixes came from an adversarial integration harness rather
than from field reports. `gameday` scenarios now drive **real** faults
against a live cluster (no more scenarios that could not fail), and the
nightly chaos gate composes them — switchover, leader pause, hard kill,
backup bursts, **DCS outage**, **compound storm** (etcd paused past the
TTL *and* the leader killed together), and **janitor sweep** (`repo gc
--apply` and `wal prune --apply` racing the streamer mid-storm) — then
verifies, restores, and **boots** the backups it took. A backup that has
never been restored is not known to be restorable; the gate makes "it
restores and serves rows" the pass condition.

Supporting that: container/volume-leak gates after the integration
suite, Windows and macOS unit lanes, docs-truthfulness guards that fail
CI when a documented flag or config key drifts from the binary, and the
long Docker soaks moved behind build tags so they run nightly rather
than on every push.

## Upgrading

Drop-in. There is no on-disk or config migration, and no change to
encryption or WORM posture on upgrade.

- **If a deployment or backup name contains a dot-delimited `tmp`
  segment** (e.g. `...tmp...`), upgrade to `1.2.2` before your next
  `repo gc` / `wal prune` / `repo replicate` — that is the one case the
  storage-walk bug could lose data (see above).
- **If you back up a TDE cluster** and want restore-target safety, add
  `--tde` (or a `tde:` block) so backups carry the `source_tde` stamp.
  Existing untagged backups still restore; they simply cannot warn a
  vanilla-PG target.
- **On Kubernetes**, the sidecar chart's keyring now works end-to-end
  via `keyring install`; if you previously worked around the keyless-pod
  bug, you can adopt the documented `keyring.existingSecret` path.
- **New CLI surface** you may want: `restore --to-latest`, `backup
  --tde`, `keyring install`, and the append-only repository mode.
